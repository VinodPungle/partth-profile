F1

Enterprise Multi-Agent AI Platform

A provider-agnostic, cloud-native platform for hosting multiple collaborating AI agents — not a chatbot, but a platform in which agents, LLM providers, memory, tools, search, and vector stores are each replaceable through configuration, without touching business logic.

  • Python
  • FastAPI
  • Azure AI Foundry
  • React
  • TypeScript
  • Bicep
  • OpenTelemetry
  • Docker
Engineering detail — architecture & decisions

The problem

Most agent projects hard-wire one vendor's SDK through the entire codebase, so swapping a model, a search backend, or a vector store means rewriting business logic. This platform treats every AI capability as a replaceable provider behind a typed interface.

Architecture & key decisions

  • Five layers with strictly one-way dependencies; exactly one package is permitted to import a vendor SDK. The abstraction has been proven in practice: switching model families across Azure subscriptions cost three environment variables and zero code changes.
  • Keyless authentication throughout — DefaultAzureCredential locally and Managed Identity in Azure, with API keys disabled at the resource level (disableLocalAuth), so a leaked key is impossible rather than merely discouraged.
  • The agentic tool loop enforces budgets between iterations — maximum tool invocations and model calls are checked where stopping still saves the next call, so an unbounded loop cannot turn one request into an open-ended bill.
  • Tool usage is streamed to the UI as a dedicated SSE event, so a turn that searches the web is visibly an agent at work rather than a blank bubble, and answers cite the search that produced them.
  • Full observability: structured JSON logging and OpenTelemetry tracing with a correlation ID propagated from HTTP request through runtime, providers, logs, and traces.
  • Delivery discipline: strict typing (mypy --strict), 600+ tests at ~95% coverage, CI quality gates on every pull request, non-root Docker images with vulnerability scanning, and the complete Azure resource graph defined in Bicep.

Role: solo project — architecture, backend, frontend, and infrastructure.

F2

FinPal — Student Financial Advisor

Conversational financial advisor where the model handles conversation and a deterministic rules engine handles arithmetic — financial figures are computed, never generated.

  • Python
  • FastAPI
  • OpenAI API
  • Groq Whisper
  • SQLAlchemy
  • PostgreSQL
  • SSE
Engineering detail — architecture & decisions

The problem

Students asking an LLM for financial advice get numbers that sound right. An advisor is only trustworthy if its figures are actually right — every time.

The central design decision

LLM-driven dialogue is kept strictly separate from a deterministic, rules-based calculation engine. The model never produces a financial figure; it interprets the question and presents the answer, while the rules engine does the arithmetic. That separation covers budget allocation, investment projections, EMI affordability, debt payoff strategies, and emergency fund calculations.

Architecture

  • Voice and text input: in-browser audio capture transcribed with Groq Whisper, replies streamed over Server-Sent Events.
  • Session persistence through the SQLAlchemy ORM on PostgreSQL/SQLite.
  • Provider-agnostic LLM layer across OpenAI, Groq, OpenRouter, and Google Gemini.

Role: solo project — design and implementation end to end.

F3

AI Virtual Tutor for a Coaching Academy

Retrieval-augmented tutoring system for IIT-JAM exam preparation, built for a real coaching academy and running in production — with mandatory specialist-model routing for life-sciences questions.

  • LangChain
  • LangGraph
  • LangSmith
  • Vertex AI
  • Google Cloud Run
  • Python
Engineering detail — architecture & decisions

The problem

Students preparing for the IIT-JAM entrance exam need accurate answers grounded in their academy's own teaching material — including live-class transcripts spoken in mixed Marathi, Hindi, and English. This was built for a real client, not as a course exercise.

Architecture & key decisions

  • An orchestrator model routes each question across specialist models, with a hard constraint: biotechnology and life-sciences questions are never answered without input from a domain-specialist model. Correctness in the exam domain is enforced by the routing graph, not left to a prompt.
  • RAG pipeline on LangChain, agent orchestration with LangGraph, and LangSmith for observability across every routed call.
  • Handles multilingual live-class transcripts (Marathi / Hindi / English); embeddings via gemini-embedding-001 at 768 dimensions on Vertex AI.
  • Models deployed on Google Cloud Run with NVIDIA L4 GPUs and scale-to-zero, so a coaching academy's budget is not spent on idle GPU hours.
  • Data minimization by design: logging is deliberately limited to student ID and first name only.

Role: built the system for the client — pipeline, orchestration, and deployment.
